integrate with solstone

your journal runs an MCP server. this page covers how to connect an agent to it or build something on it: what it offers, what you as the owner control, and where the code lives.

at a glance

what it is
a Model Context Protocol server inside your journal. any MCP client can use it.
address
/mcp on whichever route you turn on. on the journal's own computer: http://127.0.0.1:7659/mcp
protocol
MCP 2025-03-26 over Streamable HTTP. POST JSON-RPC and get JSON back. initialize returns an Mcp-Session-Id, and DELETE ends the session.
sign-in
OAuth 2.1 hosted by the journal (PKCE S256), or a key you create for a script
offers
9 tools. no resources, no prompts, no event stream, no stdio.
writes
only the agent's own notes. an agent can't add to, change or delete anything else in your journal.

connect an agent

  1. pick where the agent runs. in your journal, open agents and choose connect an agent. the route decides the address:
    the agent runsaddressdefault
    on the journal's computerhttp://127.0.0.1:7659/mcpon
    on your wifi or VPNhttps://<private address>:7660/mcpoff. uses a certificate from your journal's own authority, which the agents page offers for download.
    anywhere, through solstone.mehttps://<8 characters>.solstone.me/mcpoff. $5/yr. the relay passes encrypted bytes through, and the journal holds the certificate.
    anywhere, at your own domainhttps://<your domain>/mcpoff. the journal gets its own certificate. needs a CAA record.
  2. make a pairing code for that route. it's 8 characters, works once, and expires after 10 minutes. until a code is open, the journal won't answer a sign-in from anyone.
  3. add the address to your agent:
    agentadd itthen sign in
    Claude Codeclaude mcp add --transport http journal <address>type /mcp, choose journal
    Codexcodex mcp add journal --url <address>codex mcp login journal
    Gemini CLIgemini mcp add --transport http journal <address>/mcp auth journal
    Claude on the webadd a custom connector in Claude's settings, with your solstone.me or own-domain addressconnect it from there
    any other MCP clientadd an HTTP server at the addressit should find the OAuth sign-in on its own
  4. approve it. your browser opens a page served by your journal. choose what the agent may see (next section), enter the code, and connect.

what you control

every connection gets its own grant. you choose it when you approve the agent, and you can change it later in agents or with the solstone journal mcp commands.

policyyour choices
how much of your journalyour whole journal: everything now and anything added later, including facets you create later.
only the facets you choose: just those facets, as they grow. facets you create later aren't included.
what kinds of materialany of three:
transcripts: what was said in your recordings and imports, as text. never the audio or the screen frames.
entities: the people, places and projects your journal knows, and what it has noted about them.
facets: facet names and descriptions, and the activities, events and summaries filed in them.
its own notesalways on. every connection can save notes, and recall only the ones it saved. other agents can find them through search if their grant covers them. you can read and delete them in your journal.
where it connects froma signed-in agent only works at the route it was paired on. turn a route off in agents and nothing reaches your journal that way.
how long it lastsa signed-in agent has to pair again 30 days after pairing. a script key lasts until you revoke it.
changing your mindchange what it may see, rename a key, or disconnect it. its activity (which tools it called and with what, when, how it ended and which entries it got back, as links, never a copy) stays in your journal.

how a grant shapes what the agent sees

  • a tool that needs a kind you didn't grant is left out of the agent's tool list
  • the facet and category arguments only list what you granted, so the agent is never told about a facet it can't read
  • every call is checked again when it arrives, so narrowing a grant takes effect at once

for example, with transcripts only, limited to two facets, the agent is offered search like this. the facet values are the journal's ids for those facets, not their names:

{
  "name": "search",
  "title": "search the journal",
  "annotations": { "title": "search the journal", "readOnlyHint": true, "openWorldHint": false },
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "query":    { "type": "string" },
      "category": { "type": "string", "enum": ["transcripts"] },

      …
    }
  }
}

tools

all nine. "needs" is the kind you must grant before the tool is offered. days are YYYYMMDD or YYYY-MM-DD, and every list takes a limit of 1–100.

toolwhat it doesneedsinputs
searchsearch what this connection may see: summaries of conversations and work sessions, activities, imported documents, calendar events, and notes on people and projects. leave out the query to list what a day holds.transcriptsquery, day / day_from / day_to, category, facet, cursor
fetchread the full text of a search resulttranscriptsreference (required)
list_transcriptslist transcript segments with their times, newest days firsttranscriptsday, time_from / time_to (HH:MM), facet, cursor
get_transcriptread what was said in one segment, word for wordtranscriptsreference (required), cursor
list_entitieslist the people, projects and other entities this connection may seeentitiesfacet
get_entityread what the journal has noted about one entity: its type, description, the last day it came up, and notesentitiesreference (required)
list_facetslist the facets this connection may seenothing
save_memorysave a note of the agent's own, up to 32 KB. the only tool that writes. retrying with the same operation_id and content saves it once.nothingcontent, operation_id (both required)
recall_memoryread back this connection's own notes. leave out the query to browse.nothingquery, day / day_from / day_to, continuation, limit 1–20

the full input schemas, and the descriptions the agent itself reads, are in registry.rs. your agent sees the same thing when it calls tools/list.

build an integration

a script on the journal's computer: use a key

create a key, then grant it what it needs. a new key can only use its own notes until you grant it more.

solstone journal mcp token create --label my-script
solstone journal mcp permission set --token my-script --category transcripts --category entities
# or: transcripts from one facet only
solstone journal mcp permission set --token my-script --category transcripts --facet work

keys work at the journal's own computer and through solstone.me. the wifi or VPN and own-domain routes take signed-in agents only. token list and token revoke --label manage them, and permission show / clear manage grants.

then talk to it like any MCP server:

# start a session, and keep the Mcp-Session-Id header it returns
curl -si http://127.0.0.1:7659/mcp \
  -H "Authorization: Bearer $JOURNAL_KEY" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"my-script","version":"1"}}}'

# see what this key may use
curl -s http://127.0.0.1:7659/mcp -H "Authorization: Bearer $JOURNAL_KEY" \
  -H "Content-Type: application/json" -H "Mcp-Session-Id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

# call a tool
curl -s http://127.0.0.1:7659/mcp -H "Authorization: Bearer $JOURNAL_KEY" \
  -H "Content-Type: application/json" -H "Mcp-Session-Id: $SESSION" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"search","arguments":{"query":"lease renewal"}}}'

# end the session
curl -s -X DELETE http://127.0.0.1:7659/mcp -H "Authorization: Bearer $JOURNAL_KEY" -H "Mcp-Session-Id: $SESSION"

an app or agent other people install: use OAuth

your client signs in the way the agents above do. each route hosts its own sign-in:

discovery
/.well-known/oauth-protected-resource, then /.well-known/oauth-authorization-server
registration
POST /register: dynamic client registration, or a client ID metadata document (your own https:// URL as client_id)
authorization
/authorize with PKCE S256 and the resource from the protected-resource metadata. public clients only, no client secrets.
tokens
POST /token, authorization_code and refresh_token. access tokens last 1 hour. refresh tokens rotate on every use, and reusing an old one revokes the grant.
scopes
none. the owner picks the grant on the consent page, and your client discovers the result through tools/list.
redirects
loopback (localhost or 127.0.0.1, any port), or the exact callback of a hosted agent the journal recognises. the list

design for it: /register and /authorize answer 403 until the owner has a pairing code open, so tell the owner to make one first. the grant ends 30 days after pairing however often you refresh, so handle a failed refresh by asking them to pair again.

limits

limit
pairing code8 characters · one use · 10 minutes · one route · one open at a time
wrong codes5 per sign-in attempt. 20 from one source lock the code until you make a new one.
sessions16 per agent · end after 30 minutes idle
open connections256 at once (64 on the wifi or VPN and own-domain routes)
request body200 KB
one saved note32,768 bytes
